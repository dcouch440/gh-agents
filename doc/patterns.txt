## Router Design Notes (2026-02-01)

The first router system prompt should follow this pattern:

```
SYSTEM:
Tools you can use:
{tool configs in a line for the agent}

You are a tool router. Please use the chat history presented in front of you,
the last question asked, and the agent's added context to route the tool
request to the appropriate tool.
```

Key points:
- Tool configs are injected as compact one-liners (not full JSON schemas)
- The router sees: chat history + last question + agent context
- Routes tool requests, not general queries
- This will be used with RouterStrategy (single-round, no tool_use, temp=0.0)

## Dynamic Mode Switching (2026-02-01)

Agents can have LLM-driven "modes" that adjust config mid-conversation.

### Flow
1. User message arrives → `hub::run_chat()` loads the agent's base config
2. Pre-execution RouterStrategy pass classifies the conversation → returns a mode key
3. Mode key maps to a config overlay (system prompt suffix, temperature shift, tool set changes)
4. Overlay applied to ChatConfig, then main chat turn executes

### Proposed Schema
```sql
agent_modes (
    id UUID PRIMARY KEY,
    agent_id UUID REFERENCES agents(id),
    name TEXT,                  -- "technical", "creative", "concise"
    system_prompt_suffix TEXT,
    temperature_override FLOAT,
    tool_overrides TEXT[],
    classifier_hint TEXT        -- helps the router pick this mode
)
```

### Why This Works
- `run_chat()` takes config and executes — doesn't care where config came from
- Base agent config + overlay = dynamic personality without a separate "mode system"
- RouterStrategy already exists for single-round classification (no tools, temp=0.0)
- Completely different from the old static ModeRegistry — this is per-agent and LLM-driven

## Mode Event Tracking (2026-02-01)

No separate event table needed. The RouterStrategy classification call that picks
a mode is itself an `agent_execution` — input, output, tokens, cost all captured
automatically by ExecutionRecorder.

The only addition: `selected_mode_id UUID` on `agent_executions` so we can link
the classification result to the mode that was applied. The classifier's reasoning
is already in the execution's output column.

## Versioning Strategy (2026-02-01)

Everything user-editable should be versioned so we can reconstruct the exact
config that produced any historical response.

### Tables to version
- `agents` — system_prompt, model_id, temperature, tier changes
- `agent_modes` — any override field changes
- `tools` — parameter schema changes
- `workflows` / `workflow_steps` — step config changes
- `output_schemas` — schema changes
- `prompt_templates` — content changes

### Approach: version column + history table
Each versionable table gets:
1. `version INT NOT NULL DEFAULT 1` on the main table (current version)
2. A `_versions` history table that stores full snapshots:

```sql
agents_versions (
    id UUID,                    -- same as agents.id
    version INT NOT NULL,
    name TEXT,
    system_prompt TEXT,
    model_id TEXT,
    model_temperature FLOAT,
    -- ...all columns from agents...
    changed_by UUID,            -- user who made the change
    changed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (id, version)
)
```

### Rules
- Every UPDATE to a versionable table bumps `version` and inserts into `_versions`
- `_versions` is append-only, never mutated
- Foreign keys from execution records (agent_executions, mode_events, etc.) reference
  the entity id + version, so you can always look up the exact config snapshot
- The main table always has the current/latest version

### Priority order
1. `agents` + `agent_modes` (most impactful, modes depend on this)
2. `tools` (tool behavior changes affect execution)
3. `workflows` / `workflow_steps`
4. `output_schemas` + `prompt_templates`

## Token Ledger as Single Source of Truth (2026-02-01)

Right now token/cost data is duplicated:
- `agent_executions` has input_tokens, output_tokens, cost_usd (denormalized totals)
- `token_ledger` has per-call entries with the same fields
- `execution_messages` has per-round token counts
- `ChatStrategy` doesn't write to the ledger at all

This is a mess. Clean it up:

### Rules
1. `token_ledger` is the ONLY place cost/token data lives for accounting
2. `execution_messages` keeps per-round token counts (useful for debugging)
3. Remove `input_tokens`, `output_tokens`, `cost_usd` from `agent_executions`
   — query the ledger if you need totals for an execution
4. Every strategy (Chat, DagStep, Router) writes to the ledger via ExecutionRecorder
5. All cost dashboards, spend limits, billing queries hit the ledger

### Migration
- Add ledger writes to ChatStrategy::on_complete()
- Add ledger writes to RouterStrategy::on_complete() (for mode classification)
- Drop token/cost columns from agent_executions (or stop writing them)
- Update any queries that read cost from agent_executions to join token_ledger

## Pipeline & Workflow Cancellation (2026-02-02)

Currently there is NO way to stop a running pipeline or workflow. Pipelines can
only end via completion or internal failure. This needs to change.

### What's missing
- No `cancelled` status on pipeline_runs, stage_executions, or agent_executions
- No cancel API endpoint
- No cancellation tokens in the execution chain
- No way to interrupt an in-flight LLM call
- No UI controls for stopping executions

### Implementation

#### 1. New status: `cancelled`
Add to pipeline_runs, stage_executions, agent_executions. Treat as a terminal
state like `completed` or `failed`.

#### 2. CancellationToken
Pass a `tokio_util::sync::CancellationToken` through the execution chain:
- `run_chat()` gets a token
- `ExecutionEngine::execute()` checks `token.is_cancelled()` before each LLM round
- If cancelled mid-round, record partial results and set status to `cancelled`

#### 3. API endpoints
```
POST /api/pipeline-runs/:id/cancel     ← cancel entire pipeline
POST /api/agent-executions/:id/cancel  ← cancel single execution
```

#### 4. Token registry
`AppState` holds a `HashMap<Uuid, CancellationToken>` keyed by run_id or
execution_id. Cancel endpoint looks up the token and calls `.cancel()`.
Engine checks it on each loop iteration.

#### 5. Cascade behavior
- Cancelling a pipeline cancels all in-flight stage executions
- Cancelling a stage execution cancels all in-flight agent executions within it
- Already-completed stages/executions are NOT rolled back
