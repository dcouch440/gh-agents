## Router Design Notes (2026-02-01)

The first router system prompt should follow this pattern:

```
SYSTEM:
Tools you can use:
{tool configs in a line for the agent}

You are a tool router. Please use the chat history presented in front of you,
the last question asked, and the agent's added context to route the tool
request to the appropriate tool.
```

Key points:
- Tool configs are injected as compact one-liners (not full JSON schemas)
- The router sees: chat history + last question + agent context
- Routes tool requests, not general queries
- This will be used with RouterStrategy (single-round, no tool_use, temp=0.0)

## Dynamic Mode Switching (2026-02-01)

Agents can have LLM-driven "modes" that adjust config mid-conversation.

### Flow
1. User message arrives → `hub::run_chat()` loads the agent's base config
2. Pre-execution RouterStrategy pass classifies the conversation → returns a mode key
3. Mode key maps to a config overlay (system prompt suffix, temperature shift, tool set changes)
4. Overlay applied to ChatConfig, then main chat turn executes

### Proposed Schema
```sql
agent_modes (
    id UUID PRIMARY KEY,
    agent_id UUID REFERENCES agents(id),
    name TEXT,                  -- "technical", "creative", "concise"
    system_prompt_suffix TEXT,
    temperature_override FLOAT,
    tool_overrides TEXT[],
    classifier_hint TEXT        -- helps the router pick this mode
)
```

### Why This Works
- `run_chat()` takes config and executes — doesn't care where config came from
- Base agent config + overlay = dynamic personality without a separate "mode system"
- RouterStrategy already exists for single-round classification (no tools, temp=0.0)
- Completely different from the old static ModeRegistry — this is per-agent and LLM-driven
