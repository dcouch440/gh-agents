Notes
1
Decomp protocol generates everything. The user picks "Decomp", configures ports (agent slots), and the system auto-generates: the output schema (array of {port, content}), the prompt injection (telling the LLM about available agents + their tools), downstream steps, edges, and port wiring. No manual edge-drawing needed.
2
Multi-assignment is supported. The LLM can assign multiple tasks to the same port (e.g. two tasks to "frontend"). Each downstream step executes as for_each over its assigned items. The prompt explicitly tells the LLM this is allowed.
3
Port slots show routing. Colored dots on the right edge of the decomposer node represent output ports. Each maps to a downstream agent. Edges inherit the port color for visual traceability.
4
Room node is the fan-in point. All specialist agents' outputs feed into the Code Review room. The room has multiple input ports (left side) matching the upstream agent colors. The room processes these inputs through multi-agent conversation.
5
The generated prompt includes tools. Each agent listing in the auto-generated prompt shows the agent's available tools and capabilities, so the orchestrator can make informed routing decisions.
6
Cards are mini dashboards. Each node shows its connections at a glance: Inputs labeled by upstream step name (not raw variable names), Context showing attached files/documents, Tools showing available capabilities, and Output showing the schema or port configuration. No raw {} syntax — everything is human-readable.

Notes
1
1:1 rooms are compact nodes. A room with a single agent uses a smaller node design — just the agent avatar, name, and a chat preview. No member list needed. Same room backend, simpler visual treatment.
2
Human-in-the-loop pattern. The "Approve & Continue" button closes the room session, which triggers DAG resume. The agent's last response + any structured output becomes the step output that flows to the next step. This is how you gate workflow progression on human approval.
3
1:1 rooms can also be fully autonomous. If the room's max_turns is set to 1 and no user interaction is needed, the agent speaks once and the session auto-closes. This makes it a simple "agent processes input and you can optionally intervene" step.
4
Transform → Room → Implementation. This shows a common pattern: an AI designs something (transform protocol), a human reviews it (1:1 room), then another AI implements it. The room is the quality gate between design and execution — no review protocol needed.

Notes
1
Add is a tab on the right sidebar. The "+" icon sits at the top of the icon rail. Clicking it opens the Add panel in the same detail panel area used by Properties, Prompts, etc. Drag tiles onto the canvas to place nodes.
2
Two categories of structural nodes. Protocols are orchestration patterns (decomp, route, review, transform) that auto-expand into steps + edges when configured. Rooms are collaboration spaces where multiple agents discuss. Each creates a workflow step with special configuration.
3
Protocols expand after configuration. Drop a Decomp onto the canvas → it creates a single step node. Open Properties → configure which agents map to which ports → the system auto-generates downstream agent steps, edges, output schema, and prompt injection. The protocol node is the orchestrator.
4
The Agents tab is a drag shortcut. Instead of placing a protocol/room and then assigning agents, you can drag an agent directly from the Agents tab (or the "Recent Agents" list in the Add panel) onto the canvas. This creates a pre-configured single execution mode step — useful for simple one-agent tasks that don't need orchestration.
5
Every step gets prompt layers. After placing a node, the Prompts sidebar tab shows three stacked layers: (1) the agent's base system prompt (read-only), (2) protocol-injected instructions (auto-generated, if protocol attached), (3) step-level additions (user-editable). This lets you customize any step's behavior without modifying the underlying agent.
Section 6 Architecture summary — Protocols, rooms, and the DAG executor
System Architecture
A
Three node types on the canvas. Every workflow is composed of: (1) Protocol nodes — steps with an attached protocol that auto-generates wiring (decomp, route, review, transform). (2) Room nodes — multi-agent or 1:1 collaboration points with live chat. (3) Agent step nodes — simple single-agent execution steps. Protocol nodes auto-generate agent step nodes as downstream children.
B
Protocols are compile-time, rooms are runtime. Protocols expand into workflow primitives (steps, edges, ports, schemas) at design time — they're a UI convenience that generates the DAG structure. Rooms execute at runtime — they're a step type where agents collaborate in real-time. The DAG executor treats both as regular steps.
C
Data flow: Protocol → Agents → Room → Next. A decomp protocol fans out to N agent steps. Each agent step produces output. Those outputs feed into a room's input ports. The room's agents discuss the combined inputs. When the session closes, the room's outputs flow to the next step. The DAG executor handles all of this through normal step/edge/port resolution.
D
Rooms pause the DAG. When the DAG executor reaches a room step, it creates a room session (linked via run_id) and pauses. The session runs independently — agents take turns, users can chat in. When the session closes (POST /room-sessions/:id/close), it triggers DAG resume with the room's outputs. This is the built-in human-in-the-loop mechanism.
E
The sidebar is context-sensitive. The 5 sidebar tabs (Properties, Prompts, Agents, Schemas, Execution) show different content based on what's selected: protocol config for protocol nodes, room settings for room nodes, agent details for agent steps. The Execution tab becomes a live chat when a room node is selected.
F
No manual edge drawing for protocols. When the user attaches a protocol to a step and configures its ports, the system auto-generates all downstream steps and edges. The canvas shows the expanded result. The user can still manually add edges for non-protocol connections (e.g. agent step → room node).
G
Multi-assignment decomp → for_each. When the orchestrator LLM assigns multiple tasks to the same port (e.g. two tasks to "frontend"), the downstream agent step automatically executes as for_each. This uses the existing label-based routing system: routing_mode="label", routing_field="port", with StepRoutingRuleRow entries mapping port names to agent IDs.
H
Room structured outputs are typed. Each room member can have an output_schema_id. Their responses are validated against this schema and stored in room_execution_outputs. Downstream steps can consume specific agent outputs via port resolution using output_name as the key.
