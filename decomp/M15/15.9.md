# Ticket 15.9: System Prompt Admin

> Seed agent prompts into the database on startup and provide a super-admin UI for editing them live.

## Goal

All system agent prompts (orchestrator, worker, utility) are stored in the database. On first boot they're seeded from compiled defaults. Super admins can edit any prompt from the UI without touching code. Runtime always reads from DB.

**Checkpoint**: Prompts seeded on startup, editable via admin UI, changes take effect on next agent invocation, "Reset to default" restores the compiled version.

---

## Context

Currently prompts live in `src/prompts/` as Rust code. This ticket moves them to the database so they can be edited at runtime by a super admin.

**Key files**:
- `src/prompts/` — Current prompt definitions (become seed source)
- `src/db/mod.rs` — Database queries
- `src/server/api.rs` — API endpoints
- `migrations/` — New migration

**Dependencies**:
- Requires M10 (Server Layer) complete
- Requires M11.4 (Layout) for frontend slices

## Slices

### Slice 15.9.1: Database Schema & Seed Table

**Do this**:
- Create migration `011_system_prompts.sql`:
  - `system_prompts` table:
    - `key` (TEXT PRIMARY KEY) — unique identifier (e.g., `orchestrator.decompose`, `worker.implement`, `utility.review`)
    - `name` (TEXT NOT NULL) — human-readable name
    - `description` (TEXT) — what this prompt does
    - `category` (TEXT NOT NULL) — agent role: `orchestrator`, `worker`, `utility`
    - `content` (TEXT NOT NULL) — the prompt template
    - `default_content` (TEXT NOT NULL) — compiled default (for reset)
    - `is_modified` (BOOLEAN NOT NULL DEFAULT 0) — tracks if admin has edited
    - `variables` (TEXT) — JSON array of expected template variables
    - `created_at`, `updated_at` (DATETIME)
  - `system_prompt_versions` table:
    - `id`, `prompt_key` (FK), `content`, `changed_by` (TEXT), `version_num`, `created_at`
- DB functions: `get_system_prompt`, `list_system_prompts`, `update_system_prompt`, `reset_system_prompt`

### Slice 15.9.2: Prompt Seed Runner

**Do this**:
- Create `src/prompts/seed.rs`
- Define a `PROMPT_SEEDS` array/vec with all current prompts as `(key, name, description, category, content, variables)`
- Extract current prompt text from existing modules into seed data
- On server startup, run seed:
  - For each seed entry: INSERT if `key` doesn't exist, skip if it does
  - Update `default_content` column for all seeds (so reset always uses latest compiled version)
  - Log count: "Seeded N new prompts, M already exist"
- Call seed function from `src/server/mod.rs` during startup

### Slice 15.9.4: Admin API Endpoints

**Do this**:
- `GET /api/admin/prompts` — List all system prompts (query: `?category=`)
  - Returns: key, name, category, is_modified, preview (first 200 chars), updated_at
- `GET /api/admin/prompts/:key` — Get full prompt with content, default_content, variables, versions
- `PUT /api/admin/prompts/:key` — Update prompt content
  - Auto-creates version entry
  - Sets `is_modified = true`
  - Clears cache for this key
- `POST /api/admin/prompts/:key/reset` — Reset to default_content
  - Creates version entry noting "reset to default"
  - Sets `is_modified = false`
- `GET /api/admin/prompts/:key/versions` — Version history
- `POST /api/admin/prompts/:key/revert/:version_num` — Revert to specific version
- All endpoints require super-admin auth (add role check)

## Notes

- The seed approach means prompt code in `src/prompts/` becomes the "factory default" — it's still maintained in code but only used for seeding
- When a developer adds a new prompt in code, it auto-seeds on next restart
- The `default_content` column always reflects the latest compiled version, so "Reset to Default" gives you the newest code version even if the DB row was seeded months ago
- Consider adding a "Test Prompt" button that runs the prompt against a sample input and shows the output (future enhancement)
