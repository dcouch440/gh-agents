# Ticket 16.5: Multi-Tenant Data Isolation

> Add org_id to every tenant-scoped table and enforce isolation at the middleware layer.

## Goal

No user can ever see, modify, or access data belonging to another organization. Every query is scoped. Every endpoint is guarded.

**Checkpoint**: Two orgs exist, user in org A cannot see org B's repos, prompts, reports, tasks, or chat messages. Verified with integration tests.

---

## Context

All existing tables (tasks, agents, messages, repos, prompts, reports) need an `org_id` column. The middleware must inject org context automatically so no endpoint can accidentally forget to filter.

**Key files**:
- `src/db/mod.rs` — All queries get `WHERE org_id = $N`
- `src/server/auth.rs` — Middleware extracts org context
- `migrations/` — Add org_id columns

**Dependencies**:
- Requires 16.1 (Postgres) and 16.2 (Org model) complete

---

## Slices

### Slice 16.5.1: Add org_id to All Tenant Tables

**Do this**:
- Migration: add `org_id` (UUID, NOT NULL, FK to orgs) to:
  - `tasks`
  - `agents`
  - `messages`
  - `repos`
  - `prompts`, `prompt_tags`, `prompt_versions`
  - `reports`, `report_comments`
  - `pivotal_points`
  - `system_prompts` (org-level overrides, keep global defaults too)
  - `sessions`
  - `feed_items`
- Add index on `org_id` for every table
- Default existing data to a migration org (if any exists)

**Create/modify**:
- `migrations/` — new migration adding org_id columns

**Verify**:
- [ ] Migration runs cleanly

### Slice 16.5.2: Tenant Context Extractor

**Do this**:
- Create `TenantContext` struct: `{ org_id: Uuid, user_id: Uuid, role: Role }`
- Extract from JWT on every authenticated request
- Make `TenantContext` available as an Axum extractor (like `AuthUser` today)
- All API handlers receive `TenantContext` instead of raw auth
- Reject requests with invalid/expired org membership

**Create/modify**:
- `src/server/auth.rs`
- `src/server/api.rs` — Update all handlers

**Verify**:
- [ ] `cargo check` passes
