# Ticket 19.2: WebSocket Tool Event Protocol

> Deliver structured tool execution events to frontend clients over WebSocket, with a new `tool_events` channel and message types.

## Goal

WebSocket clients can subscribe to a `"tool_events"` channel and receive `tool_call_started` and `tool_call_completed` messages in real time. Messages carry the full structured `ToolCallEvent` data. Clients can optionally filter by agent ID.

**Checkpoint**: Frontend subscribes to `tool_events` channel → agent runs a Grep → client receives `tool_call_started` then `tool_call_completed` with `SearchMatches` output.

---

## Context

The existing WebSocket infrastructure supports channels (`feed`, `tasks`, `agents`) with typed `ServerMessage` variants. This ticket adds a fourth channel for tool events.

**Key files**:
- `src/server/ws.rs` — New ServerMessage variants, channel handler
- `src/server/state.rs` — Tool event subscription

**Dependencies**: 19.1

## Slices

### Slice 19.2.1: ServerMessage Variants

**Do this**:
- Add new `ServerMessage` variants to `ws.rs`:
  - `ToolCallStarted { data: ToolCallStartedWs }` with `serde(rename = "tool_call_started")`
  - `ToolCallCompleted { data: ToolCallCompletedWs }` with `serde(rename = "tool_call_completed")`
- Define `ToolCallStartedWs` struct (flat version for WS):
  - `tool_call_id: String`
  - `agent_id: String`
  - `agent_type_id: Option<String>`
  - `task_id: Option<String>`
  - `tool_name: String`
  - `tool_args: serde_json::Value`
  - `timestamp: String` (ISO 8601)
- Define `ToolCallCompletedWs` struct:
  - `tool_call_id: String`
  - `agent_id: String`
  - `tool_name: String`
  - `success: bool`
  - `output: serde_json::Value` (serialized `ToolCallOutput`)
  - `output_type: String` (e.g., "text", "file_list", "search_matches", "diff", "empty")
  - `error: Option<String>`
  - `duration_ms: u64`
  - `truncated: bool`
  - `timestamp: String`

**Verify**:
- [ ] Both variants serialize to JSON matching the expected frontend format
- [ ] `output_type` discriminator allows frontend to pick the right renderer
- [ ] Existing ServerMessage variants unaffected

### Slice 19.2.2: Tool Events Channel

**Do this**:
- Add `"tool_events"` to the valid channels list in `ws.rs`
- In the WebSocket connection handler, subscribe to `state.subscribe_tool_events()` when client subscribes to `"tool_events"`
- Forward `ToolCallEvent::Started` → `ServerMessage::ToolCallStarted`
- Forward `ToolCallEvent::Completed` → `ServerMessage::ToolCallCompleted`
- Convert backend types to WS types (the flat, string-ID versions)

**Verify**:
- [ ] Client subscribes to `"tool_events"` → receives `subscribed` acknowledgment
- [ ] Tool events flow to subscribed clients
- [ ] Clients NOT subscribed to `"tool_events"` don't receive them
- [ ] Existing channels (`feed`, `tasks`, `agents`) unaffected

---

### Slice 19.2.3: Agent ID Filtering

**Do this**:
- Support filtered subscription: `{ type: "subscribe", channels: ["tool_events"], filters: { agent_id: "uuid" } }`
- When `agent_id` filter is set, only forward events for that agent
- When no filter, forward all tool events
- Store filter per-connection in the WS session state

**Verify**:
- [ ] Unfiltered subscription → receives events from all agents
- [ ] Filtered by agent_id → receives events only for that agent
- [ ] Filter can be changed by re-subscribing with different filter
- [ ] Invalid agent_id filter → still subscribes (just receives nothing)

---

### Slice 19.2.4: Backpressure & Buffering

**Do this**:
- If a client is slow and the broadcast channel fills up, use `tokio::broadcast::Receiver::recv()` with lag handling
- On lag (missed events), send a `ServerMessage::Error` with message: `"Missed {n} tool events due to slow connection"`
- Consider rate-limiting: if an agent fires >10 tool calls/second, batch `Started` events (send immediately) but debounce `Completed` events to max 10/second per client
- Log a warning when backpressure kicks in

**Verify**:
- [ ] Fast tool execution (20 calls in 1 second) → client receives all events or gets lag warning
- [ ] Slow client → receives error about missed events, doesn't crash
- [ ] Normal rate → no batching, events arrive individually
