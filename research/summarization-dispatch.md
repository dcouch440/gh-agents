# Cheap Model Preprocessing for Dispatch Agents

Research on using lightweight/fast LLM models as preprocessors to summarize accumulated context before handing off to expensive builder agents. Compiled February 2026.

## Our Problem Statement

The Board Dispatcher reads a changeset from Phase 0 and dispatches configuration instructions to the Per-Node Builder for each affected node. As workflows grow, the accumulated context (conversation history, beliefs, upstream outputs, box content, annotations) drowns the builder agent. We want a cheap model (Haiku, Grok Fast, Gemini Flash) to preprocess the full context and produce a focused instruction for the builder.

---

## 1. Summarization-as-Dispatch in Multi-Agent Systems

### The Pattern: Cheap Model Preprocessor, Expensive Model Reasoner

The industry has converged on a consistent architecture: use small/cheap models for preprocessing, classification, extraction, and routing, reserving expensive models only for complex reasoning that smaller models demonstrably fail at.

**Cascade Routing** (ETH Zurich, ICLR 2025) formalizes this as "cascade routing" -- a unified framework where a small model attempts the task first, and a deferral rule determines whether to escalate to a larger model. A well-implemented cascade starts 90% of queries with smaller models and escalates only complex requests to premium models, achieving ~87% cost reduction. Quality is estimated by fitting a linear model based on uncertainty features like perplexity.

> "Cascade routing combines the adaptability of routing with the cost-efficiency of cascading... consistently outperforms both routing and cascading across various settings."
> -- [A Unified Approach to Routing and Cascading for LLMs](https://arxiv.org/abs/2410.10347)

**NEXUSSUM** (ACL 2025) demonstrates hierarchical multi-agent summarization where preprocessing converts raw content into a normalized form before the main summarization agent sees it. Their three-stage pipeline -- (1) preprocessing, (2) narrative summarization, (3) iterative compression -- achieves up to 30% improvement in BERTScore.

> Source: [NexusSum: Hierarchical LLM Agents for Long-Form Narrative Summarization](https://aclanthology.org/2025.acl-long.500/)

**Multi-LLM Agent Decomposition** (arxiv 2401.07324) proposes splitting agent capabilities into planner, caller, and summarizer, each implemented by a focused LLM. Small models handle planning and extraction; large models handle synthesis.

> Source: [Small LLMs Are Weak Tool Learners: A Multi-LLM Agent](https://arxiv.org/html/2401.07324v2)

### TierMem: The Two-Tier Pattern

TierMem introduces a provenance-linked two-tier memory hierarchy directly relevant to our problem:

1. **Fast tier (summary index)** -- compressed, structured summaries for quick access
2. **Deep tier (raw logs)** -- immutable original content, accessed only when the summary is insufficient
3. **Lightweight router** -- decides whether the summary tier is sufficient or needs escalation to raw logs
4. **Provenance links** -- every summary points back to its source material for traceability
5. **Online consolidation** -- verified findings from deep retrieval get written back to the summary tier, amortizing future costs

This maps directly to our problem. The cheap model produces the "fast tier" (focused instruction). The Per-Node Builder works from that. If the builder needs more detail, it can request the "deep tier" (full box content, belief history, raw conversation logs).

### Anthropic's Own Architecture

Anthropic's multi-agent research system uses this pattern explicitly:

> "Each subagent might explore extensively using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens), achieving a clear separation of concerns."
> -- [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

> "Multi-agent implementations typically use 3-10x more tokens than single-agent approaches, with overhead stemming from duplicating context across agents, coordination messages between agents, and summarizing results for handoffs."
> -- [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

This means the preprocessing step MUST produce genuinely compressed output. 10,000 tokens of accumulated context should become 1,000-2,000 tokens of focused instruction, or the preprocessing adds cost without reducing load.

## 2. Information Loss in Summarization

### What Gets Lost

**The U-shaped faithfulness curve**: LLMs faithfully summarize the beginning and end of documents but neglect middle content.

> "Summaries generated by GPT-4 were mostly accurate, with inaccuracies found in only 10% of cases, however, 42% of the summaries exhibited hallucinations and 47% omitted clinically relevant information."
> -- [Current and future state of evaluation of LLMs for medical summarization](https://www.nature.com/articles/s44401-024-00011-2)

**Technical details are especially vulnerable**: Factory.ai tested three compression approaches across 36,000+ messages from real engineering sessions:

| System | Accuracy Score | Context Awareness | Compression |
|--------|---------------|-------------------|-------------|
| Factory (structured) | 4.04 | 4.01 | 7-12k chars |
| Anthropic (built-in) | 3.74 | 3.56 | 7-12k chars |
| OpenAI (compact) | 3.43 | N/A | 99.3% ratio |

> "The key insight is that structure forces preservation -- by dedicating sections to specific information types, the summary cannot silently drop file paths or skip over decisions. Each section acts as a checklist that must be populated or explicitly left empty."
> -- [Evaluating Context Compression for AI Agents](https://factory.ai/news/evaluating-compression)

**The Complexity Trap** (JetBrains Research, NeurIPS 2025) found that LLM-based summarization can actually HURT agent performance:

> "Summarization caused 'Trajectory Elongation' where when an LLM summarized a failed test run, it often smoothed over the severity of the failure, causing the agent to not realize how stuck it was."
> -- [The Complexity Trap](https://arxiv.org/html/2508.21433)

Their finding: simple observation masking (hiding old environment outputs while preserving action/reasoning history) performs as well as LLM summarization and costs less. A hybrid approach yields 7-11% additional cost savings.

### Detecting Information Loss

Faithfulness evaluation is formulated as precision/recall:
- **Recall** -- how many facts from the source are retained in the summary
- **Precision** -- how many facts in the summary are supported by the source

The Q-S-E methodology generates questions from the source text, then checks if the summary can answer them. Unanswerable questions reveal omissions.

> Source: [A hallucination detection and mitigation framework](https://www.nature.com/articles/s41598-025-31075-1)

## 3. Summarize-Then-Verify Patterns

Several approaches exist for downstream agents to request more context:

**TierMem's Escalation Pattern**: Default to the summary tier. When the downstream agent finds the summary insufficient, it escalates to the raw logs tier. Provenance links guide retrieval. Verified findings consolidate back into the summary tier.

**Adaptive Dual-Mode Framework** (E-mem): "Fast Mode" (summaries) for simple tasks, "Deep Research Mode" (full episodic memory reconstruction) for complex planning. A lightweight router decides which mode.

> Source: [E-mem: Multi-agent based Episodic Context Reconstruction](https://arxiv.org/html/2601.21714)

**Practical implementation for our system** -- a two-pass pattern:

```
Pass 1: Cheap model reads full context, produces focused instruction
Pass 2: Builder reads instruction, works with it
  - If builder calls request_more_context(aspect):
    - System retrieves relevant raw content for that aspect
    - Builder continues with expanded context
```

**Google ADK's approach**: Sliding window with configurable `compaction_interval` and `overlap_size`. Their `LlmEventSummarizer` class allows specifying a different (cheaper) model with a customizable `prompt_template`.

> Source: [Context compression - Agent Development Kit](https://google.github.io/adk-docs/context/compaction/)

## 4. Conversation Compression Techniques

### Recursive Summarization

> "Errors in recursively generated summaries account for less than 10% of the memory content... LLM-generated memory actually produced better responses than ground truth memory because generated memories are more coherent and digestible for the LLM."
> -- [Recursively Summarizing Enables Long-Term Dialogue Memory](https://arxiv.org/abs/2308.15022)

Less than 10% error rate is promising, but our tolerance is lower -- we're configuring agent behavior, not generating conversational responses.

### ACON: Gradient-Free Compression Optimization

The most technically sophisticated approach. It optimizes compression guidelines in natural language space:

1. Run agent with full context -- succeeds
2. Run agent with compressed context -- fails
3. LLM analyzes the failure: "what did the compression lose?"
4. Update compression guidelines based on failure analysis
5. Repeat

Results: 26-54% reduction in peak tokens while preserving task success. Distills into smaller models preserving 95% of teacher's accuracy.

> -- [ACON: Optimizing Context Compression for Long-horizon LLM Agents](https://arxiv.org/abs/2510.00615)

### Context Rot

Chroma's research tested 18 frontier models -- every single one gets worse as input length increases. Three compounding mechanisms: lost-in-the-middle effect, attention dilution at scale, and distractor interference.

> "Coding agents are especially vulnerable because they accumulate context during multi-step tasks."
> -- [Context Rot](https://research.trychroma.com/context-rot)

This validates our approach: preprocessing isn't just cost optimization -- it's quality optimization. A focused 2,000-token instruction will produce better builder output than a 50,000-token context dump.

## 5. Production Systems Using This Pattern

### MemGPT / Letta

Memory tiers (OS metaphor): Core memory (RAM, always in-context), Recall memory (SSD, searchable history), Archival memory (HDD, vector/graph databases). Agents use tools like `core_memory_append` and `core_memory_replace` to manage their own memory. Letta introduced "Context Repositories" (Feb 2026) with git-based versioning.

> Source: [Intro to Letta](https://docs.letta.com/concepts/memgpt/), [Memory Blocks](https://www.letta.com/blog/memory-blocks)

### Mem0

Extraction Phase ingests latest exchange + rolling summary + m recent messages. An LLM extracts candidate memories (salient facts). Update Phase compares each fact to similar entries in vector DB, choosing: add, update, merge, or delete. Results: 26% improvement over OpenAI, 91% lower p95 latency, 90%+ token cost savings.

> Source: [Mem0 Paper](https://arxiv.org/abs/2504.19413)

### Claude Code (Anthropic)

Auto-compaction at 95% context usage. Summary prompt injected as user turn, structured summary in `<summary>` tags replaces message history. Preserves architectural decisions and unresolved bugs. Tool Result Clearing removes used tool outputs -- "the safest form of compaction."

> Source: [Claude Code Context Management](https://deepwiki.com/anthropics/claude-code/3.3-session-and-conversation-management)

### ChatGPT (OpenAI)

Within session: no compression, raw messages until limit. Across sessions: lightweight list of conversation summaries (user messages only). Stored memories: explicit facts injected into every prompt.

> Source: [How ChatGPT Memory Works, Reverse Engineered](https://llmrefs.com/blog/reverse-engineering-chatgpt-memory)

### Google ADK

Configurable: `compaction_interval`, `overlap_size`, `LlmEventSummarizer` (specify cheaper model), `prompt_template` (customize focus).

> Source: [Google ADK Context Compression](https://google.github.io/adk-docs/context/compaction/)

## 6. The "Game of Telephone" Problem

Galileo's taxonomy identifies 14 unique failure modes. Multi-agent failure rates: 41-86.7% in production.

> "Without shared memory solutions, agents in a chain experience 'telephone games' where the fifth agent doesn't have the same access to original research as the first."
> -- [AI Agent Handoff: Why Context Breaks](https://xtrace.ai/blog/ai-agent-handoff-why-context-gets-lost-between-agents-and-how-to-fix-it)

Solutions: structured memory (typed/linked objects), persistent storage (shared DB), provenance tracking.

> Source: [Why do Multi-Agent LLM Systems Fail](https://galileo.ai/blog/multi-agent-llm-systems-fail)

## 7. Recommendations for Our System

### Architecture: Structured Preprocessing with Escape Hatch

```
Full Context (per node) --> Cheap Preprocessor (Haiku/Flash) --> Structured Instruction --> Per-Node Builder (Smart Model)
                                                                                              |
                                                                                              v
                                                                                    request_more_context() tools
                                                                                    (escape hatch to raw data)
```

### Key Design Decisions

1. **Structured output, not free-form summary.** Factory.ai proves structured beats free-form by 0.61 points. Each section is a checklist that cannot silently omit.

2. **Preserve user language verbatim in "User Intent" section.** JetBrains' Complexity Trap shows summarization smooths over important details.

3. **Provide escape hatch tools to the builder.** TierMem pattern: default to summary, escalate to raw data when needed.

4. **Target 5:1 to 10:1 compression ratio.** Anthropic returns 1,000-2,000 tokens from subagents that explored 10,000+.

5. **Include provenance links.** Every claim references its source for trace-back.

6. **Implement ACON-style feedback loop.** When builder output is rejected, trace back to preprocessing. Was info lost? Update prompt.

7. **Consider observation masking for updates.** JetBrains found hiding old tool outputs (preserving reasoning) matches LLM summarization quality.

### Structured Output Template

Sections the preprocessor must populate (or explicitly mark empty):
- **Node Identity**: name, type, topology position
- **User Intent**: raw text from box, annotations, sketches (verbatim)
- **Upstream Context**: what flows in, from which nodes
- **Key Beliefs**: relevant beliefs (tagged, with confidence)
- **Change Delta**: before/after with what specifically shifted (verbatim, never summarized)
- **Constraints**: explicit requirements from user

### Cost Model

| Component | Model | Tokens In | Tokens Out | Cost |
|-----------|-------|-----------|------------|------|
| Preprocessor | Haiku 3.5 | ~10,000 | ~2,000 | ~$0.002 |
| Builder (with preprocessing) | Sonnet/Opus | ~3,000 | ~2,000 | ~$0.05 |
| Builder (without preprocessing) | Sonnet/Opus | ~15,000 | ~2,000 | ~$0.20 |
| Escape hatch (if triggered) | Sonnet/Opus | ~5,000 extra | ~500 | ~$0.05 |

Preprocessing saves ~75% on builder token costs for the common case.

### What NOT To Do

1. **Don't use opaque compression.** OpenAI's compact achieves 99.3% compression but sacrifices interpretability.
2. **Don't recursively summarize summaries.** Always work from raw content.
3. **Don't summarize the change delta.** Pass before/after diff verbatim.
4. **Don't preprocess when context is small.** Skip if <3,000 tokens.
